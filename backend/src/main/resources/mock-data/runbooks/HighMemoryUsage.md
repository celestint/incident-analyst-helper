# 内存异常排查（LLM 执行版）
**原则**：每次工具调用需要输出判断，供分析结果使用。

**窗口定义**：
- 告警窗口：告警开始至恢复/结束；未停止则至当前。
- 基线：告警窗口前紧邻 30 分钟。

## 1. 查内存指标
调用 `getMetrics`，body 关键字段 `metric=memory`；其他参数按工具 schema 补全。

1. 返回非空则：  
1.1 取内存时序，按时间排序。
- 优先取 NoCacheMemPerc；无则算：`(UserMem - CacheMem) / (UserMem + MEMFreeMem) * 100`。
- MEMUsedMemPerc 仅参考；无则算：`UserMem / (UserMem + MEMFreeMem) * 100`。
- 如果点数据不全 → 忽略该点，用有效点判断。  
1.2 输出判断（需基于多有效点，不能单点代“持续”）：  
1.2.1根据数据得出故障证据：
- NoCacheMemPerc 是否曾持续 >80% / >90%？持续多久？峰值？-> 如果持续，则说明内存资源饱和
- 5 分钟涨 >5% 或 15 分钟涨 >10% ？->内存快速上涨，趋势异常；
- FreeMem < 总内存 5%？->空闲内存不足  
1.2.2 如果没有故障证据，说明当前告警为什么产生：NoCacheMemPerc或MEMUsedMemPerc >80% ?  
1.2.3 如果当前告警已结束，判断最后一个有效点是否不符合故障证据  
1.3 输出判断示例（以匹配一个故障证据为例）：
- 告警未结束：[指标] 10:05-10:18 NoCacheMemPerc 曾持续 >90%，峰值 96%，已持续 7 分钟，需处理
- 告警已结束：[指标] 10:05-10:18 NoCacheMemPerc 曾持续 >90%，峰值 96%，持续 7 分钟；当前 65%，已回落。
- 告警噪音：[指标] 10:05-10:18 MEMUsedMemPerc 曾 >80%，峰值 81%，当前 65%，而NoCacheMemPerc正常，判断为噪音。

2. 返回非空则直接输出判断：[指标] 指标数据缺失，不下结论

## 2. 查错误日志
调用 `getLogs`，body 关键字段 `keyword=ERROR`；其他参数按 schema。

根据判断流程，输出判断：
1. 命中 ERROR：命中 `OutOfMemory`/`oom-killer`/`Killed process`，则判 OOM。命中`GC overhead`/`Java heap space`/`Metaspace`即判内存回收失败。
2. 未命中 ERROR：用 `count=true` 查窗口内全部日志条数。
    - 条数 >0：日志正常上报。补查 WARN（是否显示GC 频繁、heap usage high），无异常才写“日志无异常”。
    - 条数 =0：对比基线（故障前紧邻 30 分钟）。基线有、窗口无 → 疑似断档/卡死；基线也无 → 记“日志缺失”。

输出判断示例：
- 有异常：[日志] 无 OOM；WARN 命中 GC overhead，10:06 起 3 条
- 无异常：[日志] 无 ERROR/WARN，日志无异常
- 数据缺失：[日志] 日志数据缺失，不下结论

## 3. 查调用链
调用 `getTrace`，无参数；其他按 schema。

根据判断流程，输出判断：
1. 窗口内无 trace → 记“调用链缺失”。
2. 窗口内有 trace：  
2.1. 有基线（故障前紧邻 30 分钟）：
   - 基线 >0，窗口 =0 → 疑似断档 / 服务卡死。
   - 基线 >0，窗口 >0 → 查 error span、超时 span、RT 是否 > 基线、trace 是否残缺；有则异常，无则“调用链无异常”。 
2.2. 无基线：只做窗口内自检同上。无异常写“无基线可对比，窗口内未发现异常”，记“基线缺失”，不下“无影响”。

输出判断示例：
- 有异常：[调用链] 窗口有 trace，RT 120ms > 基线 80ms。
- 数据缺失：[调用链] 调用链数据缺失，不下结论

## 4. 分析结果
1. 基于指标和日志判断，确认产生原因
2. 基于调用链判断，确认影响范围
3. 基于指标判断，决定推荐SOP
- 已回落但曾经NoCacheMemPerc>80%：按事件处理，归因、防复现
- 是噪音：完善配置避免后续噪音
- 需要处理：1. 先尝试通过限流/扩容/摘除异常实例等方法止损，2. 如果快速定位需要重启则滚动重启，且重启前通过heap dump等方式保留证据
