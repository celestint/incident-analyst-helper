# 通用兜底排查手册（LLM 执行版）
**原则**：每次工具调用需要输出判断，供分析结果使用。
**适用**：未匹配到专用手册的告警。严格按本手册步骤顺序执行，禁止自由规划排查路径。

**第 0 步：告警名价值判断**
- 告警名含可辨识的服务/资源/症状语义（如 DiskIOLatencyHigh、PodRestartFrequent、PaymentTimeoutHigh）→ 提取症状关键词（如 DiskIO → disk/io；Memory → memory/oom），继续第 1 步。
- 明显测试/演示/无意义名称（如含 UITest、Test、Demo、Mock 字样，或无法辨识任何语义）→ **跳过所有工具调用**，直接按「分析结果」输出报告，判断逻辑中注明"告警名称无有效排查语义"。

**窗口定义**（仅供你内部推理使用；输出给用户时禁止出现"告警窗口/基线窗口"术语、Unix 时间戳或窗口起止范围）：
- 告警窗口：告警开始至恢复/结束；未停止则至当前。输出表述用"故障发生时间窗口"。
- 基线窗口：告警窗口前紧邻 30 分钟。输出表述用"故障发生前 30 分钟"。

**双窗口策略（每类数据通用）**：先查告警窗口；为空则补查基线窗口；两个窗口都无数据 → 记"该类数据缺失，不下结论"。

## 1. 查指标
调用 `getMetrics`（metricName 留空）一次，返回结果即全部指标数据点，**在返回结果上自行过滤分析，不需再调接口**：用第 0 步提取的症状关键词匹配 kpi_name/metricName（如 cpu/memory/disk/io/rt/success_rate），找与告警相关的指标。

输出判断：
1. 返回非空且含相关指标：[指标] 相关指标的异常表现（峰值/持续时长/时间点，基于多有效点，不单点代"持续"）。
2. 返回非空但无相关指标：[指标] 无告警相关指标，无法支撑判断。
3. 告警窗口空 → 按双窗口策略补查基线窗口：基线有数据 → [指标] 故障发生时间窗口无数据，而故障发生前 30 分钟有数据，疑似数据断档或采集异常。
4. 双窗口均空：[指标] 数据缺失，不下结论。

## 2. 查日志
**先看条数再取内容**（避免一次拉取大量日志），重点看**与告警症状相关的 ERROR/WARN**，按双窗口策略。keyword 是服务端过滤条件，每换一个关键词就是一次新的 `getLogs` 调用：

1. 调用 `countLogs`（keyword 留空）统计告警窗口内日志条数。
2. 条数 >0 → 依次调用 `getLogs`（keyword=ERROR）→ 未命中再（keyword=WARN），在每次返回的条目中判断是否与告警相关。输出判断：[日志] 命中的相关 ERROR/WARN/症状条目（时间点 + 内容摘要）；全部未命中 → [日志] 日志无告警相关异常。
3. 条数 =0 → 按双窗口策略补查基线窗口条数（`countLogs`）：基线 >0 → [日志] 故障发生时间窗口无日志，而故障发生前 30 分钟有日志，疑似断档/服务卡死；基线也 =0 → [日志] 数据缺失，不下结论。

## 3. 查调用链
调用 `getSlowSpans`，按双窗口策略。

输出判断：
1. 有数据：[调用链] 最慢 span（耗时 + trace_id + 时间点）、error/超时 span 情况。
2. 告警窗口空、基线窗口有数据：[调用链] 疑似断档/服务卡死。
3. 双窗口均空：[调用链] 数据缺失，不下结论。

**止损**：指标/日志/调用链三类数据在双窗口下均无数据 → **停止调用工具**，直接按「分析结果」输出报告。

## 4. 分析结果
1. 基于指标和日志判断，确认产生原因
2. 基于调用链判断，确认影响范围
3. 推荐SOP 按以下情形给出：
   - 是噪音：完善配置/阈值，避免后续噪音
   - 需要处理：先止损（限流/扩容/摘除异常实例/回滚等），可快速定位且确有必要再滚动重启，重启前保留证据（heap dump/日志导出等）
   - 告警已结束：结合指标是否回落判断——已回落按事件处理（归因、防复现）；未回落继续处置
4. 数据缺失（或告警名无有效语义未调工具）时如实填写，**禁止编造数据**：
   - 当前报警产生原因："可观测数据缺失，无法定位产生原因，需人工核查数据采集"
   - 判断逻辑：编号列出实际执行的查询与结果。遇到多条数据缺失（如指标/日志/调用链）合并为一点，如"指标、日志、调用链三类数据均缺失，无法判定"；未调工具时注明"告警名称无有效排查语义，未执行数据查询"
   - confidence ≤0.3，confidenceReason 说明数据缺失或告警名无语义
   - isNoise=false（数据不足以判噪音）、needsHandling=true（保守需处理）
   - 推荐SOP 给人工核查类动作（如"核查指标/日志/链路采集链路是否正常、覆盖时段是否正确"）
